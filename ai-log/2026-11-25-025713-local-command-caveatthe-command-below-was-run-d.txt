  二、讀取流程：清單查幾次資料庫

  1. 持股 LEFT JOIN 行情：1 次。沿用現在的 JPQL 寫法，只是不再選
     lots、buy_price。
  2. 全部交易：1 次，依 holding_id, trade_date, id 排序，在記憶體裡依持股分組。
  3. 除權息：provider.eventsByCode(代號集合) 1
     次。這一階段是空的，不會真的查資料庫。

  你寫的是「持股、行情、交易各查一次」。我把持股和行情合成一次 JOIN（沿用 Part
  A），總共是 2 次查詢加 1 次 provider，不會隨持股檔數增加。

  接著每一檔：
  - 轉成 TradeInput，呼叫 HoldingReplayCalculator.replay(code, trades, events, 
    close) 重播。
  - 用 V1Compatibility 算出張數、buy_price 和能不能用 1.0 改刪。
  - 組成 HoldingListItem，濾掉股數 0 的持股。

  單筆查詢走同一條路，只是條件換成 id。

  數字怎麼對到 Part A：
  - cost = 重播的 totalCost（捨入到元），marketValue = 重播的 marketValue，pnl =
    重播的 unrealizedPnl。
  - return_pct = ProfitCalculator.returnRate(pnl, cost)，用捨入後的數字算。
  - 總計照舊用
    SummaryCalculator，加總的就是每一檔捨入後的數字，所以清單加起來會等於總計。
  - Part A 的股數都是 1000
    的倍數、價格最多兩位小數，所以每個數字都剛好是整數元。重播算出來會跟 Part A
    完全一樣，由測試 1 鎖住。

  三、「可以用 1.0 修改、刪除」的判斷放在哪裡

  放在 calc/V1Compatibility.isV1Editable(List<TradeInput> trades, long 
  currentShares)。這是純函式（只看輸入、不碰資料庫），單元測試好寫。條件是：只有
  1 筆交易、是買進、股數是 1000 的倍數，而且目前股數等於那筆的股數。

  呼叫它的地方有兩個：
  - 讀取時：結果放進
    HoldingListItem.v1Editable。網頁修改頁用它決定要不要打開表單。
  - 寫入時：HoldingService.update／delete 的流程是
    a. 開交易
    b. findByIdForUpdate（SELECT … FOR UPDATE，鎖住這一列持股）
    c. 讀這檔的交易和除權息，重播
    d. 股數 0 → 404
    e. 不符合條件 → 409
    f. 寫入（修改那一筆交易，或刪除整筆持股）

  重播一定在鎖住之後才做，才不會「判斷完、寫入前」又被別人改掉。

  新增（決定 4）：沿用 F-01 的做法，整個 create 不開交易。
  - 先用短的唯讀交易查這個代號：
    - 不存在：在交易外查官方，然後用一個寫入交易同時新增持股和一筆買進（今天，da
      te_estimated = TRUE）。兩個請求同時新增時，由 UNIQUE 約束擋下，回
      DUPLICATE_CODE。
    - 存在、股數 > 0：409 DUPLICATE_CODE。
    - 存在、股數 = 0：不用查官方（名稱和市場都已經有了）。在寫入交易裡鎖住這一列
      ，再重播一次確認還是 0，才加一筆買進並回傳原本的 id。鎖住後發現已經不是
      0（別人搶先買回），就回 DUPLICATE_CODE。
  - 鎖住資料庫的期間，完全不呼叫官方 API。
