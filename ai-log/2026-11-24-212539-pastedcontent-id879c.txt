  修法 1：批次寫入後補查（排程和啟動都適用）

  位置：QuoteRefreshService.handleBatch 的 OK 分支，在 upsert 之後呼叫新的
  backfillMissingClose(market, state, today)。啟動和排程都會經過
  handleBatch，所以兩條路徑都會補到。

  流程
  1. 先找出補查對象：這個市場有人持有（findByMarketOrderByCodeAsc），而且 quote
     的 close_price 是 NULL，再排除今天已經補查過的代號。
  2. 對每個代號呼叫該市場逐檔 client 的 lookupLatest(code, today)。
     - 這個方法會在當月往前找最後一個有成交的日子；當月整個月都沒成交時，再查上
       個月。
     - 例如 11/24 查 2363，會拿到最近交易日 11/23、收盤價 10.00（11/20）。
  3. 每個請求之前都隨機等 3.2～5.8
     秒，第一個也要等，因為前一刻剛送過批次請求給同一台主機。
  4. 依查詢結果處理：

  │          結果           │        處理方式         │ 記成「今天已補查」？ │

  │ ）                      │ 寫入（沿用 Quote.apply  │ 是                   │

  │ ）                      │                         │                      │

  「一天只補查一次」的紀錄：放在 MarketRefreshState，上市、上櫃各一份。內容是「
  哪一天」加上「當天已補查的代號集合」。日期跟今天不同時清空。集合用
  ConcurrentHashMap.newKeySet()，因為同一個市場的不同輪可能在不同執行緒上跑。

  為什麼這個紀錄有實際作用：如果假伺服器不管問哪一天，都固定回 11/23
  的資料，排程每一輪都會走到批次
  OK，但永遠不會「今天完成」。沒有這個紀錄，同一檔股票每一輪都會被重查。

  限制：紀錄只存在記憶體，重新啟動後同一天會再補查一次。你說記在記憶體即可，所以
  接受這個限制。

  修法 2：新增持股時補查收盤價

  MarketResolver 新增方法 lookupLatestInMarket(code, market, deadline)
  - 只呼叫那一個市場的逐檔 lookupLatest。
  - 共用原本的號碼牌（同時查詢上限）、執行緒池、時間預算：等待上限是「剩下的預算
    − 緩衝」和 lookupTimeout 比較短的那個。
  - 這個方法不丟例外，失敗、逾時、被擋、名額已滿，一律回 UNAVAILABLE 或
    BLOCKED。
  - 號碼牌照 F-01 的做法，等請求真的結束才歸還。

  HoldingService.create：快取命中、但 closePrice == null 時：
  - 市場、名稱照樣用快取的。
  - 呼叫 lookupLatestInMarket(code, 快取的市場, deadline)。查到 FOUND 就用原本的
    saveQuoteQuietly 寫入；其他結果只寫 log。
  - 不論補查結果如何，持股都照常新增。
  - 這一步在 insertHolding
    之前、沒有交易的狀態下執行，和原本查官方的位置一致（F-01 的規則）。

● 可以用 JDK 內建的簡易網頁伺服器當假官方伺服器，不需要另外安裝任何東西，也不用
  Qiao 的伺服器。下面的步驟我還沒實際跑過，只是對照程式確認過。

  原理

  java -m jdk.httpserver 是 JDK 18 以後內建的靜態檔案伺服器，你目前預設的 java
  是 25，可以用。它有兩個特性剛好適合這次測試：

  - 只看路徑、不看查詢參數：不管程式問哪一天、哪個代號，都回同一個檔案。這正好模
    擬 Qiao 的情境：批次永遠是 11/23 的資料，2363 那天是 --。
  - 檔案不存在就回 404：把逐檔的檔案改名，就能模擬「批次正常、逐檔失敗」。

  對照程式：
  - 程式不會檢查回應的日期是不是查詢的那一天（TwseMiIndexClient
    用表標題裡的日期）。
  - 404 會被當成查不了（FAILED／UNAVAILABLE），不會當成被擋。

  所以這個做法可行。
